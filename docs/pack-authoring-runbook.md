# Pack-authoring runbook — point this engine at a new application

Written for someone who is not the author. Follow it top to bottom; every
command is meant to be typed as printed. Part A is the proof path on the
personal machine (it rebuilds the InvoiceGuard pack from nothing). Part B is
the work machine: a known-good rehearsal on InvoiceGuard first, then the real
target application on real data, ending in `engine serve` in a local browser.
Appendix A is the failure list, written so a chat assistant can read it and
hand an investigation to a coding assistant.

## 0. Before you start

**Two machines.** The personal machine (macOS, this repo, the OpenRouter key)
authors everything and proves the procedure. The work machine (Windows,
Python 3.12, `uv` through the enterprise package proxy, no Claude Code) runs
the demo: `git pull` in, nothing out — not a push, not a file. Anything that
must come back is photographed off the screen, so every step below that
produces a result says **photograph this** and keeps that result short.

**Tokens.** None for the repository: while it is public the work machine
pulls anonymously. One token for Databricks: a personal access token from
the workspace, valid for Foundation Model serving and for the SQL warehouse.
It goes in an environment variable, never in a file in the repository.

**Names.** No real name of the target application, the production pack or
the enterprise workspace enters this repository, in a file or a commit
message. The real pack lives in `packs/local-<name>/`, which `.gitignore`
excludes; the workspace host lives in an environment variable. On the
personal machine `uv run python scripts/leakage_grep.py` checks the tree
and history against a term list that is itself gitignored.

**Environment variables** (set in the shell that runs `engine`):

| variable | machine | value |
|---|---|---|
| `DATABRICKS_HOST` | work | `https://<workspace host>` |
| `DATABRICKS_TOKEN` | work | the personal access token |
| `PYTHONUTF8` | work | `1` — the reports use non-ASCII characters; the Windows console does not, by default |
| `OPENROUTER_API_KEY` | personal | the OpenRouter key (only `engine ask`, `engine serve` and `engine eval run` need it) |

PowerShell: `$env:DATABRICKS_HOST = "https://..."`; cmd: `set DATABRICKS_HOST=https://...`.
`engine info` works without any of them, and says which adapter each port
resolved to.

**What a pack is.** One directory. Machine-written files are regenerated by
`engine` and never hand-edited; human-written files are yours.

| file | written by | read by |
|---|---|---|
| `config.yaml` | you | everything — adapters, tools, generation, pull, UI |
| `app.duckdb` | `engine convert` or `engine pull` | run_sql, the generators, the validator (gitignored) |
| `substrates/*.jsonl`, `substrates/manifests/*.json` | `engine generate` (and the pull/convert manifest) | every tool |
| `components.yaml` | you | the CKG generator, the primer check |
| `primer.md` | you | the app_primer tool, the CKG generator |
| `dictionary_map.yaml` | you | run_sql's grounding — the semantic layer |
| `overlays/dictionary.jsonl`, `overlays/component_memberships.jsonl` | you (human rows) | merged in by `engine generate`; regeneration never touches them |
| `business_docs/*.md` | you (snapshots with front matter) | search_business_docs |
| `work.db` | the engine at run time | conversations, published units (gitignored) |

## Part A — the personal machine: rebuild InvoiceGuard from scratch

This is the acceptance proof for this document: every step is typed as
printed, in a fresh clone, and every improvised step is a defect in the
document. Start in the directory that will hold both repositories side by
side (the pack's config names the application as `../../../invoice-guard`
from inside the pack directory).

**A1. The target application, at the pinned commit, simulated.**

```
git clone https://github.com/chad-adams-firebase/invoice-guard.git
cd invoice-guard
git checkout 761a18e9b9253870d930f1b13b3a852ce516d603
uv sync
uv run invoiceguard simulate --seed 42
cd ..
```

`simulate` writes `simout/invoiceguard.db` (the application's SQLite
database after ninety simulated days) and `simout/logs/invoiceguard.log`. It
refuses to overwrite an existing `simout/`.

**A2. The engine, green.**

```
git clone https://github.com/chad-adams-firebase/substrate-engine.git
cd substrate-engine
uv sync
uv run pytest
```

Expect every test to pass offline; the count is the last line. Eight
tests report `skipped` at this point — the pack-integration tests, which
need the `app.duckdb` that A3 builds; after A3, `uv run pytest` again shows
them passing and no skips.

**A3. The world and the substrates.**

```
uv run engine convert  --pack packs/invoiceguard
uv run engine generate --pack packs/invoiceguard --check
uv run engine generate --pack packs/invoiceguard
uv run engine validate --pack packs/invoiceguard
```

`convert` reads the SQLite file named in `generation.source_sqlite` and
writes `packs/invoiceguard/app.duckdb` plus its manifest. `generate --check`
regenerates every machine substrate to a scratch directory and byte-compares
it with the committed files: `check: 6 substrate files byte-identical` is the
proof that this machine reproduces the pack. `generate` then writes them; the
only change `git status` shows is the `extracted_at` line of each manifest.
`validate` prints the conformance report and ends `RESULT: PASS`.
`generate` on InvoiceGuard prints a dozen `matches no component` warnings
for its `models` modules and one `has no member modules`; they are known
(the reference pack maps components to the spine and the platform, not to
the model layer) and harmless. Then `uv run pytest` once more: every test
passes, none skipped.

**A4. One question through the whole engine.** Needs `OPENROUTER_API_KEY`.

```
uv run engine ask --pack packs/invoiceguard --show-evidence "How many invoices received last week had findings?"
```

This is the smoke test the Brief prescribes (§3): a question that needs a
tool result before it can answer, never "hello" — a provider that mishandles
the tool-message round trip fails here and nowhere earlier. Expect exit code
0, an answer with a count, and `run_sql` in the evidence. Record the
question, the tools used and the exit code.

**A5. The browser.**

```
uv run engine serve --pack packs/invoiceguard --port 5050
```

Open `http://127.0.0.1:5050`, ask the same question, stop the server with
Ctrl-C. (macOS holds port 5000 for AirPlay; the default port works on
Windows.)

## Part B — the work machine

### B0. Step 0: does the model answer from here?

With `DATABRICKS_HOST` and `DATABRICKS_TOKEN` set, and an endpoint chosen
from the workspace's Serving page — a chat endpoint that lists function
calling as supported (a Claude or GPT pay-per-token endpoint does):

```
uv run python scripts/fm_smoke.py <endpoint>
```

One request, one tool. Exit 0 and a `tool_calls` line naming `ping` mean the
endpoint is reachable, the token is accepted, and the model calls tools.
**Photograph this.** Anything else: Appendix A, "Step 0".

### B1. Pull, sync, test

```
git pull
uv sync
uv run pytest
```

**Photograph the last line** of `pytest`. The count must match the personal
machine's. `uv sync` fetches only prebuilt wheels through the proxy;
`docs/wheel-audit.md` is the list of what it will ask for.

### B2. Rehearsal: InvoiceGuard on the Databricks model

The InvoiceGuard clone and its `simout/` already exist on the work machine
as a sibling of this repository. Copy the pack under a local name — the copy
is gitignored, so its config can name the endpoint — and switch its model:

```
Copy-Item -Recurse packs\invoiceguard packs\local-invoiceguard
```

In `packs\local-invoiceguard\config.yaml`, replace the `llm:` block:

```yaml
  llm:
    adapter: databricks_fm
    settings:
      model: <endpoint>
```

(The eval bank was never run on this route — it is the demo's route, not a
model-pin change. Leave the committed pack alone.) Then the same four steps
as Part A, on the copy:

```
uv run engine convert  --pack packs/local-invoiceguard
uv run engine generate --pack packs/local-invoiceguard --check
uv run engine validate --pack packs/local-invoiceguard
uv run engine ask --pack packs/local-invoiceguard --show-evidence "How many invoices received last week had findings?"
uv run engine serve --pack packs/local-invoiceguard
```

`--check` byte-identical proves the generators behave on this machine as on
the personal one; `validate` PASS and an exit-0 answer with `run_sql` in the
evidence prove the whole engine runs against the Databricks model. Open
`http://127.0.0.1:5000`. **Photograph** the check line, the report and the
answer. Only now touch real data.

### B3. The real target application

**B3.1 The skeleton.** Create `packs\local-<name>\` with this `config.yaml`
(every `<...>` is yours to fill; the block loads as printed — a test in the
suite checks that):

```yaml
name: local-<name>
description: <one line about the application>

substrates:
  - data_dictionary
  - data_dictionary_map
  - univariate_statistics
  - code_knowledge_graph
  - ckg_components
  - primer
  - source_code
  - application_database
  - business_context_docs

tools:
  - query_univariate_stats
  - lookup_data_dictionary
  - traverse_code_knowledge_graph
  - run_sql
  - read_source
  - app_primer
  - search_business_docs
  - answer_from_known_items
  - app_capabilities

adapters:
  llm:
    adapter: databricks_fm
    settings:
      model: <endpoint>
  sql:
    adapter: duckdb
    settings:
      database: app.duckdb
  work_store:
    adapter: sqlite
    settings:
      database: work.db
  identity:
    adapter: fake_user
    settings:
      username: demo
      display_name: Demo User
  source_code:
    adapter: local_directory
    settings:
      root: <path to the application's source directory>
      commit_sha: "<the sha from B3.2>"
  substrate_store:
    adapter: pack_files
    settings: {}

generation:
  component_id_prefix: <short prefix, e.g. app>
  source_globs:
    - "src/**/*.py"
  exclude_globs:
    - "src/**/tests/**"

pull:
  warehouse_id: <sql warehouse id>
  catalog: <catalog>
  schema: <schema>
  page_rows: 20000
  tables:
    - name: <table>
      key: <its unique, sortable column>
    - name: <another table>
      key: <its key>

ui:
  app_name: <Application> Knowledge
  accent_color: "#2f6f5e"
  starter_prompts:
    - <a question a manager would ask first>
    - What does this application do?
  capabilities: >-
    <two sentences on what can be asked, told as the pack wants it told>
```

Two things are deliberately absent: the `application_logs` substrate and the
`check_execution` tool, and with them the `execution_log` adapter — the
demo has no execution log (the Splunk design is a deployment note). A pack
drops a tool by leaving it out of `tools:`; the engine builds only what is
listed and refuses a tool whose port is not configured.

Also create `components.yaml`, `primer.md` (B3.4) and an empty `overlays\`
directory; `business_docs\` is optional.

**B3.2 The source, pinned.** The application's source is a directory on the
work machine. The engine reads it at a commit it can verify, so mint one:

```
cd <path to the application's source directory>
git init
git add -A
git commit -m "pin for the pack"
git rev-parse HEAD
cd <back to substrate-engine>
```

Put that SHA in `source_code.settings.commit_sha`. Set `source_globs` to the
application's Python files and `exclude_globs` to what the knowledge graph
should ignore (tests, migrations, vendored code). `engine generate` refuses
to run when the directory's HEAD is not the pinned SHA — a re-pin is a
deliberate act.

**B3.3 The data, pulled once.**

```
uv run engine pull --pack packs\local-<name> --dry-run
```

prints, per table, the statements the pull would run — `DESCRIBE HISTORY`,
`SELECT COUNT(*)`, and the first two pages — with no network and no
credentials. Read them; they are what a warehouse administrator would ask to
see. Then:

```
uv run engine pull --pack packs\local-<name>
```

Every table is read `VERSION AS OF` its current Delta version, so all of its
pages see one snapshot and the manifest records `schema|table@version` for
each. The summary is one line per table and the manifest id. **Photograph
this.** It is the pin of the demo's world.

Paging: set `key` on every large table — a unique, sortable column (the
primary key). Keyset paging is the intended path; a table without `key` is
paged by offset over `ORDER BY ALL`, correct on a versioned snapshot but
slower, and older warehouse runtimes reject `ORDER BY ALL` (Appendix A). A
view or a non-Delta source has no history: give it `versioned: false`. A
demo world smaller than the table: `where: "<column> >= '<date>'"` on that
table.

Numbers: warehouse `DECIMAL` columns land in the local world as `DOUBLE`
(the engine's statistics recognise `DOUBLE`; every world so far has been
`DOUBLE`-only). A currency sum in the local world can therefore differ from
the source system in the last cents. That is the type mapping, not an engine
bug — do not spend a work-side debugging session on it.

**B3.4 The application, in your words.** Two human files the generators
consume:

`components.yaml` — the application's L1 components, one entry each, ids
`<prefix>.<group>.<slug>`; copy InvoiceGuard's file for the form. A
component is a thing a person would name when describing how the
application works (the intake poller, the rules engine, the queue). The
knowledge graph assigns every source file to a component by path, so the
groups should follow the package layout.

`primer.md` — one page, L0: what the application is, for whom, what it does
each day, in the words a new colleague would need. Front matter first, as in
InvoiceGuard's primer (`source: machine`, `needs_validation: true`,
`confidence: 0.5`, a `note:` saying where it came from). Every component the
primer names must exist in `components.yaml`; `engine generate` errors on an
unknown one and warns on a component the primer never mentions.

**B3.5 Generate.**

```
uv run engine generate --pack packs\local-<name>
```

Writes the dictionary and statistics from `app.duckdb`, and the knowledge
graph from the source, with a manifest each. Warnings name what they are
about; fix the pack, not the output.

**B3.6 The semantic layer: `dictionary_map.yaml`.** This is run_sql's
grounding — what turns a question into the right SQL — and the one file
that takes real authoring time. Copy InvoiceGuard's file for the form and
start with a minimum:

- the `provenance:` block (source `machine`, confidence `0.5`,
  `needs_validation: true`, a `note:` saying where the knowledge came from);
- `concepts:` five to ten — the nouns a manager uses, each with a
  `definition`, the `tables` it lives in, and `synonyms`;
- `metrics:` two or three — the numbers people ask for, each with
  `tables`, `aggregation_sql`, and `notes` on the join and the window;
- `join_paths:` the joins that matter, one `steps` list each; note a
  composite join explicitly, or the counts multiply;
- `examples:` three or more questions with `guidance` — the single most
  effective section: each is a worked answer the model reads before writing
  SQL;
- `gotchas:` what you already know goes wrong (a status column that is a
  history, an adjustment flag, a NULL that means "not applicable").

`column_formats:` and `entities:` can wait. Every table and column the map
names must exist in the dictionary; `engine validate` says which do not.

**B3.7 Validate.**

```
uv run engine validate --pack packs\local-<name>
```

One line per check, `RESULT: PASS` at the end; a failing check lists at most
eight details and a count. **Photograph this.** Fix and re-run until PASS.

**B3.8 Ask, then serve.**

```
uv run engine ask --pack packs\local-<name> --show-evidence "<a question whose answer needs a count from the data>"
uv run engine serve --pack packs\local-<name>
```

Exit 0 with `run_sql` in the evidence is the demo's first working turn.
**Photograph the answer.** `http://127.0.0.1:5000` is the demo. Exit codes:
1 error, 2 unverified, 3 refused, 4 asked to clarify, 5 escalated — each
is a legitimate outcome, and Appendix A says what each means.

### B4. Freezing the demo world

The demo's world is `app.duckdb` plus `substrates\` plus their manifests.
Nothing regenerates on its own: `engine serve` reads and never writes them.
Before the demo, photograph `engine info --pack packs\local-<name>` and the
`manifest_id` lines of `substrates\manifests\*.json`; with them the world is
reproducible (the pull manifest names the table versions, the others the
source commit). Do not re-pull before the demo: a re-pull reads the tables
at their new versions, changes the manifest id, and requires
`engine generate` again. `work.db` is the demo's memory (conversations,
published units); keep it, or delete it to start clean.

## Appendix A — when a step fails

Each entry is what the assistant at work needs to turn a failure into an
investigation: the observable, where it comes from, what it means, and the
question to put to the coding assistant. Diagnosis first — the fix is
described in chat, made on the personal machine, and pulled back.
`docs/real-adapter-notes.md` has the same form for the two adapters and the
environment.

**Step B1, `uv sync`: "No solution found" or a package with no matching
wheel.**
Where: the enterprise proxy; the list is `docs/wheel-audit.md`.
Meaning: a dependency has no `cp312`/`win_amd64` wheel, or the proxy has not
cached it yet. The audit is clean on the personal machine, so the second is
more likely.
Ask: "Which package and version is `uv` asking for, and does the proxy's
index page list a `py3-none-any` or `cp312-win_amd64` wheel for it?"

**Step B1, `pytest`: a test fails that passes on the personal machine.**
Where: the failing test's file; `tests/test_architecture.py` if it is an
import rule.
Meaning: a Windows difference — path separators, console encoding, file
locking — in the code under test, not the rule.
Ask: "Read the failing assertion and the function it calls; which
Windows-specific behaviour (path, encoding, an open file) would produce
this value?"

**Step B0 / any ask: `UnicodeEncodeError` on the console.**
Where: any `print`; the reports carry `—` and `…`.
Meaning: `PYTHONUTF8` is not set in this shell.
Ask: nothing to investigate; set it and re-run.

**Step B0: no tool call, HTTP 401/403/404, a `tools` error, a TLS error.**
Where: `src/engine/adapters/llm_databricks_fm.py`, the docstring's table,
`DatabricksFmLLM.complete`.
Meaning: that table, row by row.
Ask: the question in the matching row.

**Step B2/B3.3, `engine convert` or `engine pull`: `PermissionError`
`[WinError 32]` on `app.duckdb`.**
Where: `pull_databricks.pull` / `convert_sqlite.convert`, the `unlink`.
Meaning: a running `engine serve` (or an open DuckDB session) holds the
file; Windows will not delete an open file.
Ask: nothing to investigate; stop the server and re-run.

**Step B3.2, `engine generate`: "source is pinned to ... but HEAD is ...".**
Where: `src/engine/cli.py`, `_verify_pinned_sha`.
Meaning: the source directory's commit is not the one in `config.yaml` —
you edited and committed, or `git init` happened after the SHA was copied.
Ask: nothing to investigate; `git rev-parse HEAD` in the source directory,
put that SHA in the config, regenerate.

**Step B3.3, `engine pull`: any `error:` line.**
Where: `src/engine/packtools/pull_databricks.py`, the docstring's table,
`_Warehouse.execute`.
Meaning: the row whose observable matches — 401/403/404, a `FAILED`
statement with the warehouse's own message (table not found, no SELECT,
`DESCRIBE HISTORY` on a view, the inline limit, `ORDER BY ALL`), a count
mismatch, an unmapped type.
Ask: the question in the matching row. For `near 'ALL'`: set `key` on that
table so the pull pages by key; for the inline limit: lower `page_rows`.

**Step B3.5, `engine generate`: "primer references unknown component" /
"no files matched source_globs".**
Where: `src/engine/generators/ckg/primer_check.py`;
`src/engine/generators/ckg/__init__.py` for the globs.
Meaning: `primer.md` names a component id absent from `components.yaml`;
or the globs, relative to `source_code.root`, match nothing.
Ask: "List the component ids in components.yaml against the ids the primer
mentions" / "Which files under the source root would `src/**/*.py` match?"

**Step B3.7, `engine validate`: a `[FAIL]` line.**
Where: `src/engine/validate/conformance.py`, the method named like the
check (`_check_manifest_links`, `_check_dictionary_map`, ...).
Meaning: the details name the row, edge, or map entry; the map's
references must exist in the dictionary, the dictionary must match the
database, machine rows must link to a recorded manifest.
Ask: "Read the check's method and the first detail line; which file in the
pack does it read, and what would make that detail true?"

**Step B3.8, `engine ask`: exit 1 with a traceback.**
Where: the last frame of the traceback names the file.
Meaning: an engine error, not a model answer; the adapters' docstrings
cover their own.
Ask: "Read the last two frames; is the failure in an adapter (network,
credentials) or in the engine (a substrate row it did not expect)?"

**Step B3.8, `engine ask`: exit 2, 3, 4 or 5 — unverified, refused,
clarify, escalate.**
Where: `--show-verdict` prints the verifier's claim-level detail.
Meaning: these are answers, not failures: the verifier could not confirm a
figure (2), the engine declined to guess (3), the question had two readings
(4), or the question is outside the pack's knowledge (5). A demo question
that returns 2 or 3 usually means the map lacks the join or the metric the
question needs.
Ask: "Read the verdict; which claim was unmatched, and which table or metric
would the map need to ground it?"

**Any turn: the answer arrives without the verified badge, and nothing
else is wrong.**
Where: `src/engine/verifier/judge.py`, the `except` around the judge call.
Meaning: a judge-model call timed out or failed; by design that is silent
and costs the badge, not the turn. If it repeats, the endpoint is slow.
Ask: "Does the smoke script answer within a few seconds right now?"

## Appendix B — substrate break-glass

Plan of record: the generators produce every machine substrate. If they
cannot run at work and the demo must go on, a substrate file can be built by
hand, by copying the form of InvoiceGuard's `substrates/*.jsonl` and filling
rows from the real code and the pulled data. Two rules keep the shortcut
honest: every hand-built row carries `"source": "human"`,
`"needs_validation": true` and no `manifest_id` (a human's row is not an
extraction artifact — the contract rejects a human row with a manifest id),
and `engine validate` must still pass. Dictionary rows and component
memberships belong in `overlays/` — `engine generate` merges them and
regeneration never touches them — and only the knowledge-graph files ever
need writing directly. Record in the pack's README which files were built by
hand.

## Appendix C — if the Statement Execution API is disabled

The workspace may have the SQL Statement Execution API turned off; then
`engine pull` returns HTTP 404 on a warehouse that exists. The break-glass is
the `databricks-sql-connector` package (a Thrift-over-HTTPS client; its
dependencies all ship Windows wheels as of this writing) driven by a small
script that writes the same DuckDB file and manifest — discovered at work,
built on the personal machine, and never the plan of record.

## Appendix D — verifying a QA session at work

Three tiers, cheapest first. Each is in the same form as Appendix A so the
chat assistant can hand the check to the coding assistant.

**Tier 1 — the engine's own verdict.**
Where: the badge on the answer; `engine ask --show-verdict` for the
claim-level detail; `engine turns --pack ... --evidence` for the evidence
bundle of any past turn.
Meaning: "verified" means every figure in the answer was matched to a value
the tools returned and passed the plausibility bounds; "unverified" means
at least one was not. The verdict is about faithfulness to the tool
results, not about the tool results being what the question meant.
Ask: "Read the verdict; which claim matched which evidence value, and was
the SQL that produced it the query the question needed?"

**Tier 2 — gold: the same figure by independent SQL.**
Where: the pulled world, `packs\local-<name>\app.duckdb`, opened read-only
with DuckDB (`uv run python -c "import duckdb; ..."`), never through the
engine; `src/engine/eval/world.py` is the referee's own read handle and the
form to copy.
Meaning: gold is always executed SQL, never a figure remembered or reasoned
to — write the query a careful analyst would write, run it against the
same snapshot, compare. A disagreement is a finding about the map (a join,
a window, a filter) or about the question, and is what the demo's
follow-up questions are made of.
Ask: "Write the SQL that answers this question directly against app.duckdb,
run it, and compare each figure with the answer's; if they differ, name the
join or filter that differs."

**Tier 3 — Genie, for spot-checks and second opinions on the source.**
Where: the workspace's Genie space over the same catalog and schema the pull
read.
Meaning: Genie reaches the live tables, the engine reaches the snapshot; a
spot-check compares one figure across the two, and a second opinion is
Genie's SQL for the same question, read against the map's `join_paths`.
Neither is gold: Genie's figure comes from tables that may have moved since
the pull's `VERSION AS OF`, and its SQL is a guess to be read, not a result
to be trusted. Use it to notice a discrepancy, then settle it in Tier 2.
Ask: "Ask Genie the same question, take its SQL, and run that SQL against
app.duckdb: does the snapshot give the engine's figure or Genie's?"
